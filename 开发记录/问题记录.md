# 有价值的问题记录

只记录以后仍可能复用的问题。每条至少写清现象、原因、解决方法和验证证据。

## 2026-09-03：偶数行棋盘和上重素材不能用“中间格/外框中心”代替视觉中心

- 现象：地图心核设置在 `(5,2)`，其 Sprite 节点确实位于一个格心，但完整棋盘为 `11×6`，真实中心位于第 3、4 行之间；结算心核的 `64×64 TextureRect` 虽然水平居中，心核素材的大部分不透明像素集中在上方，仍显得偏上。
- 影响：逻辑坐标与控件外框测试均会通过，但玩家在实际画面中仍能清楚看到地图地标和结算图标不居中；更换分辨率或同类非对称素材时问题会重复出现。
- 原因：偶数行棋盘不存在单一中央格；此前地图对象只支持格坐标锚点。结算测试只比较 `TextureRect` 外框中心，没有测量当前纹理的 alpha 加权视觉重心；心核 `96×96` 画布的 alpha 视觉重心相对画布中心约上移 `5.83 px`。
- 解决方法：为地图对象增加 `board_center` 锚点，由完整棋盘边界计算几何中心；对心核纹理逐像素计算 alpha 加权质心并缓存偏移，地图 Sprite 和结算 TextureRect 都把该质心对齐到各自目标点。结算目标点取标题底部与正文顶部之间的几何中点。
- 验证：`tests/mvp_smoke.gd` 独立扫描纹理 alpha 并断言地图心核视觉重心与棋盘中心重合、结算心核视觉重心与标题/正文间中心重合；Godot AI MCP 运行态返回地图目标/实际均为 `(483,275)`，结算目标 `(260,113)`、实际 `(260,112.99999)`；macOS `start/death/victory` 三种画面捕获通过且人工复核无上偏。
- 遗留风险：alpha 质心是稳定的程序化视觉近似，但极亮小区域或强方向性光晕可能与人眼主观重心不同；用户仍应在实际显示尺寸下确认，必要时只增加有记录的小幅艺术偏移，不能破坏棋盘几何基准。

## 2026-09-02：透明画布中心不等于角色的可见轮廓中心

- 现象：玩家、普通敌人、泥浆喷吐者和 Boss 的 `Sprite2D.position` 都落在逻辑格中心，但生成贴图每帧的透明留白不对称，实际可见轮廓仍偏离地砖中心；泥浆弹和危险格也有同类问题。
- 影响：逻辑移动和碰撞虽然正确，画面却表现为角色/投射物“站偏格”，换方向、换动作或替换新素材后偏移量还会变化；仅手调一个统一锚点不能稳定修复。
- 原因：Atlas 帧或单帧状态图的几何中心来自整张画布，不代表不透明像素包围盒中心；旧实现只为玩家维护过手工中心表，敌人、Boss 和特效没有统一使用当前运行时纹理校准。
- 解决方法：按角色类型、方向、动作帧和实际纹理区域计算 alpha 不透明包围盒中心，把其与目标逻辑格/`3×3` footprint 几何中心的差值缓存为绘制偏移；hurt/death 独立图和特效首帧采用相同方法，避免每帧重复扫描纹理。
- 验证：`tests/mvp_smoke.gd` 对玩家、窃能幼体、泥浆喷吐者、泥鳃的 4×4 主表和四方向 hurt/death 做实际轮廓中心断言，并检查泥浆弹/危险格使用格心；困难房与 Boss 房的 Godot AI MCP 运行时截图、macOS `mud/boss` 捕获均确认可见主体落在对应格心或 Boss footprint 中心。
- 遗留风险：未来更换纹理、帧尺寸或图集布局时必须继续走 alpha 中心缓存并扩展回归；半透明光晕若被纳入轮廓可能影响视觉中心阈值，需按素材类型重新确认 alpha 门槛。

## 2026-09-02：Boss 视觉体型、逻辑占格和攻击范围必须共用一个权威定义

- 现象：泥鳃此前视觉上约为 `3×3` 格巨体，状态层却只占一个中心格；横扫表现没有明确起点/深度，第四拍还把单位向中心强制拉动，导致身体边缘、可攻击位置与危险范围难以判断。
- 影响：玩家会进入 Boss 画面覆盖的格子、攻击贴近身体却可能判作远程，横扫预警与实际伤害可能漂移；吸附位移还会打断按拍走位的可预测性。
- 原因：视觉缩放、敌人占用判断、玩家攻击目标、横扫绘制和伤害判定各自使用了不同的单格/半径假设，没有由状态层提供同一组 footprint 与 sweep cells。
- 解决方法：在状态层建立 `3×3` 九格 Boss footprint，并让敌人占用、移动阻挡和边缘攻击统一查询该集合；横扫由状态层返回从 footprint 外缘开始、沿朝向延伸三格的扇形格集合，视图和伤害共同消费；第四拍改为无位移、无伤害的后摇，删除 suction intent、pull payload、拉拽函数和运行时特效引用。
- 验证：回归断言九个占格、边缘可攻击、footprint 不可进入、完整水平横扫七格、范围三格、扇形内受伤、第四拍不移动/不扣血且代码无 suction/pull；Godot AI MCP 运行态再次返回九个占格和七个扇扫格，并显示双环蓄力、连续扇面及“外缘 3 格”文字。
- 遗留风险：当前 `3×3`、三格纵深和水平七格扇面属于第一层试玩参数，仍需用户确认战斗手感；未来若修改体型或范围，只改视觉会重新产生漂移，必须先改状态层权威集合并同步测试。

## 2026-09-02：结算心核自动扩尺寸、到达动画缩放和竖直帧锚点

- 现象：死亡结算面板的 `TextureRect` 在设置纹理和拉伸模式后采用源图 `96×96` 的固有尺寸，但位置仍按 `64×64` 计算，心核可见图形向右偏；进入新房间时新玩家 Sprite 先以默认 `1×` 创建，再以 `0.72×0.88` 进入动画并放大到正常比例；玩家 atlas 的逐帧偏移依赖手工表，重新生成素材后竖直方向容易再次漂移。
- 影响：死亡结算的视觉中心不稳；换房第一帧出现“小模型突然变大”；重生或替换玩家动作表时，竖直移动可能偏离地砖中心。
- 原因：`TextureRect` 的 intrinsic-size negotiation 覆盖了早先的 `size=64`；`show_room_arrival()` 对到达表现同时动画了 `scale`；帧中心表没有从当前运行时纹理重新计算。
- 解决方法：在 `TextureRect` 完成 expand/stretch 配置并加入面板后，再设置固定 `64×64` 并按面板宽度计算水平位置；`set_room()` 先同步布局演员并为新 Sprite 设置角色比例；到达动画只改变位置/透明度并锁定正常比例；玩家 atlas 通过实际 alpha 不透明包围盒缓存逐帧中心偏移，保留旧表作为异常回退。
- 验证：`tests/mvp_smoke.gd` 新增结算心核固定尺寸/居中、到达动画前中后比例恒定、竖直移动实际不透明轮廓同列并落点居中的断言；`FIRST_LAYER_ASSETS_OK`、`DIRECTIONAL_STATES_SMOKE_OK`、`PROTO_001_SMOKE_OK`、`FONT_SMOKE_OK`、`MVP_SMOKE_OK` 通过；macOS Compatibility `action/vertical/transition/death` 输出 `MVP_CAPTURE_OK`；Godot AI MCP 运行态记录 `EndingCore=(64,64)`、面板宽 `520`、玩家比例始终 `(1.875,1.875)`，日志无脚本错误。
- 遗留风险：上述证据来自 macOS 编辑器/Compatibility 渲染，仍需用户实际键盘试玩和另一台实体 Windows x86_64 电脑验收；若未来替换非玩家角色 atlas，仍应为对应角色补同类中心回归。

## 2026-08-30：BHai 透明请求仍返回棋盘格 RGB 特效原图

- 现象：在 Chrome 的学校 BHai 页面用 `gpt-image-2 / high / 2K / 1:1` 生成右墙出口与无文字弹刀特效后，下载文件均为 2048×2048 RGB PNG；画布边缘和对象间是浅色棋盘格，未携带 alpha 通道。
- 影响：原图不能直接作为 Godot 透明特效贴图；若直接缩放会把棋盘格带入画面。原图透明请求与实际下载格式不一致，必须在台账中分开记录。
- 原因：当前 BHai 页面未提供可验证的 true-alpha 开关，模型把透明背景视觉化为棋盘格后再以 RGB PNG 返回。
- 解决方法：保留两张原图不改写；在 `tools/process_generated_assets.py` 新增 `fit_effect_sheet()`，按四个 512×2048 源单元做边界连通去棋盘格、二值 alpha、统一中心枢轴和确定性缩放，输出 192×64 与 128×32 RGBA 运行时 PNG。
- 验证：`assets/generated/bhai/derived_manifest.json` 记录两张原图与派生图 SHA-256；运行时两张图尺寸和模式分别为 `192×64/RGBA`、`128×32/RGBA`，alpha 值均仅 `{0,255}`；四帧边界与帧序通过视觉检查，原图保持棋盘格仅作为溯源文件。
- 遗留风险：专用特效尚未导入/接入 Godot，仍未完成右墙转场和弹刀捕获回归；企业/学校公开再分发授权仍未确认。若 BHai 后续提供真实 alpha 开关，应重新验证而不是覆盖当前原图。

## 2026-08-24：Universal macOS 导出要求 ETC2/ASTC 纹理导入

- 现象：首次执行 macOS 导出时，Godot 拒绝导出并提示：禁用 ETC2 ASTC 纹理格式时无法为 Universal 和 arm64 导出。
- 影响：Windows x86_64 构建可以正常生成，但 macOS DMG 无法生成，跨平台初始化验收不完整。
- 原因：工程使用 Universal 2 macOS 模板，其中包含 `arm64`；新建的空工程尚未启用 ETC2/ASTC VRAM 纹理导入设置。
- 解决方法：在 `project.godot` 的 `[rendering]` 中加入 `textures/vram_compression/import_etc2_astc=true`，随后重新导入工程并执行 macOS release 导出。
- 验证：DMG 成功生成并通过 `hdiutil verify`；只读挂载后，应用为 `arm64 + x86_64` 双架构，代码签名有效，导出的应用实际无界面启动并输出 `INIT_SMOKE_OK`。
- 遗留风险：以后若更换渲染器或纹理压缩配置，需要同时复测 macOS 与 Windows 正式构建，不能只以编辑器运行正常作为依据。

## 2026-08-26：GDScript 无法从动态脚本实例继续推断局部类型

- 现象：把房间状态拆成独立预加载脚本后，Godot 解析 `var target := player.cell + direction` 等语句时报错 `Cannot infer the type`，导致依赖该脚本的正式场景无法加载。
- 影响：节拍、房间和 UI 文件本身已经存在，但 headless 回归在进入玩法逻辑前就因编译失败退出。
- 原因：`player` 和 `enemy` 来自动态预加载脚本实例，当前文件没有为它们声明静态类型；GDScript 因而无法沿属性访问继续确定局部变量的 `Vector2i` 或数值类型。
- 解决方法：在动态脚本边界之后为局部量显式声明类型，例如 `var target: Vector2i = player.cell + direction`；UI 从未标注类型的节拍对象读取数值时，同样显式声明 `float` 或 `int`。
- 验证：修正后 `tests/proto_001_smoke.gd` 在 Godot 4.7.2 headless 下退出码为 0，并输出 `PROTO_001_SMOKE_OK`；正式入口额外运行 20 帧无解析或运行时错误。
- 遗留风险：以后新增动态加载的资源或脚本对象时，仍可能在 `:=` 处遇到同类错误；若跨文件类型长期稳定，可进一步为成员补充明确类类型，而不是只依赖局部标注。

## 2026-08-27：BHai 图生图拒绝小尺寸像素参考图

- 原因：BHai 在上传阶段要求图片的宽和高均至少为 300px；这与提示词、模型或输出分辨率无关。
- 解决方法：只裁取实际需要的玩家朝下 idle 单帧，以最近邻插值放大为 `512x512` RGBA 上传参考图，保存为 `assets/generated/bhai/references/player_idle_down_ref_512.png`；任务单改为上传此文件。放大版仅供图生图识别身份和轮廓，不能替换 Godot 的运行时精灵。

## 2026-09-04：慢拍输入被错误归属到下一拍并造成级联失拍

- 现象：上一拍输入偏慢时，基于最近拍点四舍五入的归属逻辑可能把输入当作下一拍过早输入；下一拍被锁定后，玩家按正常节拍继续操作会继续落到后续错误状态，形成连续失败。
- 影响：节拍判定、玩家行动锁和下落音符的操作感受不一致；一次偶发慢拍会污染后续多拍，直接影响第一层战斗可玩性。
- 原因：`get_input_timing()` 只按当前拍中心到输入时间的最近拍点计算，未区分“上一拍已结算后的死区”和“当前拍的有效窗口”。
- 解决方法：以当前拍与上一拍中心的中点作为过去侧归属边界。当前拍之前且更接近已结算上一拍的输入标记为上一拍迟到并拒绝消耗当前拍；当前拍未来侧仍归当前拍，保留原有过早/迟到 miss 规则。音频 cue、视觉 beat 和下落音符均继续从同一拍点与 `chart_offset_seconds` 派生。
- 验证：`tests/proto_001_smoke.gd` 新增上一拍迟到、当前拍可命中、谱面延时和 cue 单次发射断言；`tests/mvp_smoke.gd` 新增第一层节拍归属、开始页/设置页和滑条更新断言；两套脚本在 Godot 4.7.2 headless 下分别输出 `PROTO_001_SMOKE_OK`、`MVP_SMOKE_OK`。Godot AI MCP 3.2.4 运行态确认游戏可启动，开始页/设置页可见，泥浆弹标记清晰，最终 game 日志无项目脚本错误。

- 解决方法：使用 `tools/process_generated_assets.py --transition-only` 按内容读取原图，统一派生到 `assets/transitions/` 的 960×540 正确 PNG；`MvpController` 根据 Boss 所在楼层映射四张图，使用全屏 `TextureRect` 淡入，并保留程序绘制转场作为普通房间移动和资源缺失时的后备表现。
- 验证：`tests/mvp_smoke.gd` 的 `transition_assets` 断言、`MVP_CAPTURE_OK | layer_transition1/2/3/ending_transition`、`PROTO_001_SMOKE_OK`、`UPPER_LAYERS_SMOKE_OK`、`FONT_SMOKE_OK`、两个 Python smoke 和 `git diff --check` 均通过。
- 遗留风险：raw inbox 的错误扩展名仍可能让 Godot 编辑器扫描输出导入错误；目前运行时只加载派生 PNG，最终是否改名 raw 文件需另行授权；用户仍需试玩转场文字、时长和画面连续性。

## 2026-09-04：Boss 特效和奖励图标原图为 RGB 棋盘格，需要派生后接入

- **现象**：新生成的 6 张 Boss 特效和 3 张奖励图标文件虽然扩展名为 PNG，但均为 2048×2048 RGB，没有真实 Alpha；特效内容按四组横向排列在方形画布内。
- **影响范围**：直接作为运行时透明精灵会显示棋盘格；直接作为横向动画表无法满足现有 4 帧 Sprite2D 接口；新增三种奖励在原有 UI 映射中会显示空图标。
- **原因**：生成服务的透明请求实际返回 RGB 棋盘格画布，逻辑帧边界与运行时尺寸需要确定性处理。
- **解决方法**：保留 `assets/generated/bhai/inbox/` 原图不变；在 `tools/process_generated_assets.py` 增加 `--upper-boss-effects-only`，对特效执行边界连通棋盘格清理、四帧切分、二值 Alpha 与 64×64 固定帧输出，对奖励图标执行相同背景清理并输出 32×32 RGBA；运行时只引用派生目录。
- **验证方式**：检查 6 张特效均为 256×64 RGBA、3 张图标均为 32×32 RGBA；Godot 4.7.2 headless 编辑器扫描无脚本解析错误；`tests/mvp_smoke.gd` 与 `tests/upper_layers_smoke.gd` 分别验证五种增益图标映射和六种 Boss 特效调度。
- **遗留风险**：视觉动画的节奏、旋转方向和大小仍需用户试玩；raw 文件错误扩展名/编辑器扫描噪声仍遵守既有处理边界；Windows x86_64 和公开再分发授权未验收。
